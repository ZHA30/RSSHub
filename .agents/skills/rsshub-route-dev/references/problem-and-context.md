# 问题与系统上下文

## 目标

把用户请求转成可实现、可验证的 route 改动范围。先识别受影响的系统和责任边界，再定义需求，随后评估实现方案。

## 系统上下文

```text
内容源及其接口 → RSSHub route → middleware / feed 序列化 → feed reader 用户
                                      ↘ Radar 发现入口
```

| 参与者/系统 | 需要确定的责任 |
|---|---|
| 订阅者 | 订阅什么对象，需要哪些内容、排序和更新行为 |
| 内容源 | 哪些字段和接口有文档、公开样本或获准的运行证据 |
| route | 如何映射订阅身份、请求上游、形成 feed 并报告失败 |
| RSSHub 核心 | 哪些 middleware、参数、缓存和序列化行为已经提供 |
| Radar | 源站页面如何发现并映射到具体 route |
| 维护者 | 上游变更、配置、运行失败和兼容迁移由谁处理 |

访问范围按用户任务和会话中已有授权判断，具体见 `source-integration.md`。将源码仓库上游 `DIYgod/RSSHub` 与 route 的内容源分开：同步代码和请求站点是两种操作，不能用其中一种的证据替另一种下结论。

## 需求基线

按任务规模简要固定以下需求；小修复可直接从已知事实开始，不必填完整表格。

| 需求类别 | 示例问题 |
|---|---|
| 功能 | 订阅的站点、栏目、作者、标签、搜索、榜单或对象是什么？哪些 item 应进入 feed？ |
| 消费者接口 | path、参数、channel/item 字段、顺序、空结果和兼容性如何表现？ |
| 数据质量 | 日期、canonical link、正文、附件和唯一标识来自什么事实？缺失时如何表达？ |
| 运行约束 | 允许访问哪些数据？需要什么配置？请求、并发、时延、缓存有哪些边界？ |
| 失效与维护 | 上游变化、限流、解析失败或配置失效时，谁能发现并处理？ |

把要求分为**已确认事实、设计假设、待验证事项**。假设必须说明影响；若它会改变公开 path、数据访问授权、消费者语义或运行成本，先与用户澄清。

## 验收条件与追踪

每个关键需求至少对应一个实现位置或验证观察；不要用“构建通过”代替 feed 语义验收。

| 需求 | 设计/实现位置 | 可接受证据 | 状态 |
|---|---|---|---|
| 订阅身份稳定 | namespace/path/parameters | metadata、example 与源站导航/样本一致 | 已知/未验证 |
| 字段语义可信 | source mapping 与 `DataItem` | 字段来源可追溯；获准样本或静态证据 | 已知/未验证 |
| 失败可辨识 | 错误处理与配置边界 | 空 feed 与上游/解析/授权错误区分 | 已知/未验证 |

证据强度要匹配结论：静态源码证明代码路径，类型检查证明类型关系，构建证明构建状态，运行样本只证明该环境和该次观察到的结果。

## 任务裁剪

- 新增 route：至少固定订阅身份、公开接口、来源、字段来源和失效语义。
- 兼容修复：固定已有消费者可观察行为及不可变边界。
- path/数据语义迁移：分析现有用户/Radar 入口、兼容方案和回退条件。
- 排障/review：从可复现观察开始，区分事实、根因假设和证据缺口。
- metadata-only 改动：只追踪受影响的 route contract，不扩成抓取设计任务。
