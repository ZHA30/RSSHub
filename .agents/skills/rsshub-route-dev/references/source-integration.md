# 上游集成设计

## 数据来源决策

先列出必须输出的字段，再按覆盖度、稳定性、访问约束和维护成本选来源。常见优先级：

1. 官方 RSS/Atom 或页面声明的 alternate feed。
2. 文档化、公开且稳定的 API/结构化数据。
3. 静态 HTML。
4. 只有必要数据依赖浏览器执行且访问获授权时，才使用 browser automation。

样本或源码不是内容源实时行为的证明。用户明确要求检查指定公开站点、修复其路由或执行本地实例测试时，可在该任务范围内正常请求公开页面与接口，不重复要求用户证明站点所有权。仅有静态审查任务或涉及登录、凭据、非公开数据时，不推定额外访问授权。不得绕过登录、权限、签名校验、验证码、WAF 或反自动化措施；遇到阻断时报告真实结果。

对每个字段记录来源证据：官方文档、样本、静态代码推断，或获准的运行观察。列表响应不证明详情正文完整；字段缺失不证明需要认证。未知应标为假设，不能伪装为源站事实。

## 请求与解析边界

实现前固定 endpoint、method、query/body、必要 headers、响应格式、编码、分页、timeout、重试和限流语义。遵循公开接口文档和 RSSHub 当前工具：

- 复用仓库 fetch/config/parse helper；JSON 已解析时不要重复 `JSON.parse`。
- 新请求优先使用 `@/utils/ofetch`，沿用项目的代理、响应大小、重试和错误处理；旧 `@/utils/got` 是兼容封装，不套用外部 got 包的 API 假设。需要非 UTF-8 数据时以当前封装返回的 ArrayBuffer/Buffer 行为为准再解码。
- GraphQL 等结构化请求使用明确 schema/变量；不要把用户输入拼进查询语句。
- API 所需 hash 若会随构建变化，应按目标仓库规则从公开页面或响应中获取，不要硬编码；不得为此绕过访问控制或私有签名校验。
- 同一 HTML 只 `cheerio.load()` 一次；相对链接用 `new URL(raw, base).href` 归一。
- 非 UTF-8 响应按 buffer 与明确字符集解码。
- timeout、重试、并发和请求总量有界；只对适合重试的失败有限重试，并尊重限流语义。
- 对 RSSHub route 只请求源站第一页，不实现上游翻页或向用户暴露分页参数。用 `@/utils/route-limit` 的 `getRouteLimit(ctx, 默认候选数)` 控制抓取候选数和详情请求数，不手写 `ctx.req.query('limit')` 截取逻辑。它在 common filters 存在时保留候选池；middleware 先筛选再截取最终 `limit`，不能在 route 中抢先缩小候选池而改变筛选语义。
- 只添加源站文档或获准样本能证明必要的 headers。不要硬编码伪装浏览器的 `User-Agent` 或 `Referer`，也不要用它们绕过阻断。
- 解析缺关键字段或遇到错误页时，返回清楚、可操作的错误；区分有效空 feed、上游失败、解析失败和配置/授权问题，不泄露凭据，也不把失败伪装成空 feed。
- 不实现访问控制、私有签名校验或反自动化机制的绕行；接口要求未经授权的凭据时停止并说明依赖。

## 详情请求与资源预算

只有列表来源不能满足必要字段时，才增加详情/正文请求。评估请求数量、并发、源站负载、延迟和缓存失效：

- 对可复用的详情、全文、媒体补全、profile 或 taxonomy 使用目标仓库的 `cache.tryGet()`；优先稳定唯一 key，例如 `<namespace>:<kind>:<stable-id>`。
- `lib/utils/cache/scope.ts` 在 handler 运行时隔离 namespace；同一 namespace 内的不同路由仍须避免 key 冲突。共享详情缓存只保存与展示模式无关的对象，标题、链接模式和榜单顺序等输出选择在读缓存后组合。
- 缓存解析后的可复用对象，避免只为复用而缓存原始 HTML；只有下游确实需要原文时才缓存原始响应。
- cache key 不包含凭据、个人标识、临时授权材料、nonce 或临时下载 URL。
- 轻量请求可并发；高成本请求和 browser 需要限制并发，避免每个 item 启动 browser。
- fallback 只能返回真实摘要或省略可选字段；不能制造正文、日期或重复 link。
- 认证状态由目标仓库正式支持的 config/secret 机制管理，不当作普通业务缓存。认证失败应清楚暴露，不以缓存或重试掩盖权限失效。

## 配置与 Browser

- 静态页面或结构化响应足够时不引入 browser。只有目标数据确实依赖 JS 执行，且授权范围允许时才使用。
- 按当前 Route 类型声明 `features.requirePuppeteer` / `requireConfig`；仅在 handler 确有依赖时设置。
- 必需配置缺失时使用项目现有配置错误；可选配置只能增强数据，不能让无配置路径返回假结果。
- 凭据由谁提供、轮换方式和失效行为必须明确。cookie、token、完整授权头不得出现在源码、示例、radar、日志或公开缓存 key。
- 不用固定 sleep 代替内容条件；browser 用 selector 或数据响应等待必要状态。用 `page.route()` 配置资源类型 allowlist 并中止其余请求，不用只拦截少数类型的 blocklist。不要在 `Promise.all()` 循环中为每个 item 启动 browser session；在成功与异常路径都 `await` 关闭 page/context 或调用仓库清理 helper。
- 权限/阻断页是失败状态，不是空 feed；配置 feature 和缺失配置错误必须与真实依赖一致。
